SubAgents 工程化交付体系
以一支 Agent 团队取代四支职能团队的串行接力

依据《星澜科技需求》与《AI 工程概论》，将「产品 / Coding / 质检 / 项目管理」四支职能团队的边界损耗，重构为一名 FDE（融合交付工程师）指挥的三域 SubAgents 团队。人只在两端做判断——定义标准、验收结果；中间执行全部交给 Agent 按 SOP 完成。

1 名 FDE × 10 席 Agent 三域：项目管理 / Coding / 品控 双仓：ai-assets × <project> 五阶段流水线 × 六道质量 Gate 有罪推定：证据不足即退回 PDCA 管理循环：不跳步 · 不带病交付 安全铁律：凭据用而不见 AI 覆盖率 20% → 70% → 90%+ 人均项目数 N人/1项目 → 1人/3项目+

摘方案摘要

三句话看懂本方案：诊断结论、组织重构、量化目标。

核心判断

星澜的交付瓶颈不是「人不够努力」，而是组织形态：四个职能团队串行接力，信息在人的层层翻译中持续损耗。缺的不是 Agent、不是场景、不是 Token，而是工程化——可复制、可衡量、不因人而异的交付体系。

01现状诊断

五十人规模的软件定制公司，按「产品 → Coding → 质检 → 项目管理」四支职能团队串行接力交付。客户以物流、制造行业为主（物流 EHS 平台、设备监控系统、合规文档系统）。编码交付长期受制于四个职能团队之间的边界损耗，本质是四个「重复劳动黑洞」。

① 需求在层层翻译中失真

给物流客户做 EHS 平台，客户口头说的是「危化品告警」，写进 PRD 变成了通用阈值告警，上线演示当天才发现客户要的是分区联动的应急处置流程——就这一个词，返工近一个月。需求评审来回拉锯三四轮是常态。

病根信息从客户 → 产品 → Coding → 验收，每一层翻译都是一次损耗；「人」成了链条中最不稳定、最难校准的环节。

② 编码在重复造轮子中内耗

登录、权限、消息推送、报表导出——每个新项目都从零重写一遍。粗算下来新项目里过半代码与上一个项目高度相似，但一直没人有余力把这些东西沉淀成可复用的资产。

病根CRUD、接口、表设计等模式化劳动高度重复；经验没有资产化，资产没有版本化，Agent 没有上下文可加载。

③ 测试在工期压力下被牺牲

排期一紧，先压缩的就是测试，只保核心路径过一遍。这两年交付的项目，不少在上线后头一两个月都是客户现场边用边修，售后返修吃掉了团队大量工时。

病根质量靠人盯不靠机制兜底；没有评估闭环，产出不合格没有拦截，直接流向下游与客户。

④ 经验随人员流动而流失

去年一名核心开发离职，他手上几个项目的关键逻辑大多在他脑子里，接手的同事拖了一个多月才敢动第一个需求。

病根组织记忆装在个人脑子里，不在系统里；能力的私有属性导致「人走，经验清零」。

本质判断：术已就位，治未跟上。方法、工具、SOP 不是没有，而是组织形态没变——部门仍按职能分，执行仍靠人，经验仍随人走，验收仍靠自觉。工程化还没有成为硬约束，因此「拒绝标准化」与「以招人堆产能」两类反工程化行为会持续把组织拉回老路。本方案的第一性目标：重构交付组织形态，而不是增加工具。

对标 AI 工程化三大命题

  • 可复制：否——成功项目经验没有沉淀为模板与 Skill，下一个项目从零手搓。
  • 可衡量：否——产出按人天工时衡量，没有 AI 覆盖率、人均项目数、Token 计量。
  • 不因人而异：否——同一件事换个接手的人，结果与周期天差地别。

对标 AI Native 成熟度

按五维 AI 原生度自测，星澜当前处于 L0–L1（传统/试点组织）：AI 是外挂，个别员工私下提效；有 POC 但普遍卡在死亡谷；资产未入库、SOP 写给「人」、计量口径仍是人天。本方案的目标是把组织形态推向 L2（工程化组织），并向 L3（组织长在 AI 上）迈进。

02解决方案总览

用工程化方法重构交付组织形态：一支 SubAgents 团队取代四支职能团队的串行接力，一名 FDE 在两端（定义标准、验收结果）做判断，中间执行全部交给 Agent 按 SOP 完成。

支撑体系的三大支柱

资产库：代码库 + Agent 库

把登录/权限/推送/报表导出等模式化模块沉淀为可复用资产；把每一份 SOP、模板、Skill 按代码库方式管理（目录、README、Git、PR）。可复制性 = 组织的可复制性——新项目装载资产包，而不是从零手搓。组织级资产库 ai-assets 与项目级工作区 <project> 物理分离、各自独立 Git 仓库，目录规范见 §03。

流程库：面向 Agent 的 SOP 2.0

SOP 写给 Agent，不写给人：每份含四要素（触发场景 / 调用步骤 / 输入规范 / 产出验收）。Agent 没有情绪、不会遗忘、不跳槽，SOP 可以写到「一字不差地执行」的精度。

运行总线：Token 治理 + 计量看板

按项目/Agent 分组配 Token 额度、实时核算消耗；工程化计量看板按月晾晒（AI 覆盖率、人均项目数、Gate 通过率、Token 产出比），进月度经营会。

边界与安全底线

覆盖范围

所有新立项定制开发项目，从需求到部署全流程按新体系交付；存量项目维持现有维护模式，不回头改造。

安全铁律（不可妥协）

所有账号、密码、API 密钥等凭据，一律只在本地配置和使用，零穿透到大模型服务。Agent「使用」凭据但从不「看见」凭据——凭据不出现在 prompt、上下文、日志、复盘记录里。通过本地 .env.local、MCP 工具授权与沙箱隔离实现：Agent 只能通过受控工具调用凭据完成鉴权，无法读取明文、也无法把凭据带入对话。ReviewAgent 设凭据泄露扫描 Gate（G-sec），发现明文凭据即拦截并告警。

每层 README 索引

每个目录（至少到二级）必须有一份 README.md，作为该层的「门牌」——供人导航、供 Agent 定位。README 四要素：

  • 这层放什么：目录职责一句话说清；
  • 子目录用途：每个子目录一行说明（目录名即语义，README 补上下文）；
  • 命名与落位规则：什么产物进这里、怎么命名；
  • 质量指针：本层产出对应哪道 Gate、由哪个 Agent 验收。

OPCTEAM.md：Agent 进入即读的上下文锚点

每个仓库（ai-assets 与每个 <project>）根目录必须存在 OPCTEAM.md。任何 Agent 开始任何任务前，第一步是读取所在仓库的 OPCTEAM.md——它一次讲清五件事：

  • 仓库身份与边界：这是资产库还是哪个项目；允许做什么、禁止做什么；
  • 目录地图：产出去哪、输入从哪取（与各层 README 互为入口）；
  • 关键 SOP 指针：本场景对应的 SOP 2.0 位置（ai-assets/docs/sop/…）；
  • 当前状态与验收标准：项目所处阶段、Gate 状态、验收条件；
  • 安全红线：凭据仅本地 .env.local、零穿透大模型服务；Agent 用而不见——凭据不入 prompt / 上下文 / 日志 / 复盘记录。

OPCTEAM.md 是「不因人而异」的技术起点：任何人驱动任何 Agent，进入仓库先读同一份锚点，上下文不再依赖操作者的口头描述。

04三域协作结构

十席 Agent 按「项目管理域（编排中枢）→ Coding 域（执行）→ 品控域（质量把关）」三域组织。PMAgent 是唯一的编排中枢，向两端辐射：向上对接 FDE 的标准与验收，向下调度 Coding 域执行、接受品控域闸门裁决。

FDE（人）：唯一的人机界面

FDE = 行业经验 × Agent 编排能力 × 工程化交付方法。人不在流程中间，只在两端：

上游 · 校准者：把客户的模糊需求定义成 Agent 可执行的清晰标准——验收条件可度量、SOP 无歧义、契约先行。
中段 · 编排者：审阅 PMAgent 的任务拆包与 Gate 裁决，处理异常升级事项（超过最大重试次数、跨域争议、需求变更）。
下游 · 验收者：依据 G6 证据包做最终验收；随机抽人驱动 Agent 校验「不因人而异」；批准上线与移交。

FDE 不需要写代码。他写的是自然语言指令、验收清单与 Gate 规则——AI 负责把指令翻译成代码、测试与部署。

管理域工作过程：PDCA 四步循环（不得跳步 · 不得带病交付）

项目管理域由 PMAgent 主持，以 PDCA 驱动每个阶段与整条五阶段流水线：Plan 定目标 → Do 按 SOP 执行 → Check 用质量 Gate 与量化指标核验 → Act 达标放行并复盘沉淀。四步严格顺序执行，不得跳步；Check 未通过不得放行，不得带病交付。

P · Plan定目标：阶段计划 / 任务派发单 / Token 预算 / 量化目标
→
D · Do按 SOP 执行：派发 Coding / 品控，全程采集数据
→
C · CheckGate 核验：证据自证清白，量化比对目标
→
A · Act达标放行 + 复盘蒸馏，回写下一轮 Plan
三条铁律：① 不得跳步——P→D→C→A 严格顺序执行；上一轮 Act 未完成（复盘未沉淀、数据未回写资产库）不得开启下一轮 Plan。② 不得带病交付——Check 检出缺陷未清零的产出不得放行；确需放行的已知风险必须登记为豁免项、由 FDE 签字批准，并进入 Act 的整改清单。③ Check 不合格即退回——退回 Do 修复，重跑 Check，直至达标或升级 FDE。

各 Agent 的 SOP 2.0（面向 Agent · 四要素齐备）

三域全部 10 席 Agent 各配一份 SOP，按四要素书写：触发场景（何时执行，条件无歧义）、调用步骤（先做什么后做什么）、输入规范（格式与校验，不清晰即拒）、产出验收（怎么判定做完且做好）。SOP 归档于 ai-assets/docs/sop/（文件名 <agent>.sop.md）；Agent 启动任务时先读所在仓库 OPCTEAM.md，再加载对应 SOP。产出验收即对应质量 Gate 的证据包构成，与 §05 Gate 一一挂接。

协作模式与编排纪律

流水线接力（主模式）

需求 → 设计 → 开发 → 测试 → 部署，段间有质量 Gate，Gate 不通过产物退回上游、不流向下游。上一段产出不通过，下一段不启动。

并行编排（提速）

契约先行解耦后，Backend / Frontend / Api 三席并行开工；任务粒度相当、接口契约明确、由 PMAgent 汇总校验。目标：并行耗时 ≤ 串行 50%。

Swarm 转交（兜底）

边界不清的任务允许跨域 handoff（如 ApiAgent 发现契约歧义转交 ArchitectAgent），附带完整上下文；设最大转交次数，超限回退 FDE 人工介入。

契约先行

Agent 间只认接口契约与产物规范，不认人、不读对方内部实现。交接产物固定格式（架构 JSON、接口 YAML、任务包清单）。

硬超时 + 异常降级

每个 Agent 有硬超时，卡死即标记失败并触发备用路径/告警；单项目 Agent 故障不影响其他项目。失败数据记录并回写，积累为改进输入。

全景看板

PMAgent 维护统一看板：哪个 Agent 在运行 / 等待 / 报错 / 已完成，Gate 通过率、Token 消耗、覆盖率读数，供 FDE 随时查看。

编排纪律（从 2 个开始、先串后并）：不要一上来就编排十席。先让每个 Agent 在职责范围内独立可靠（单 Agent 质量缺陷会在编排中被放大），再逐步增加并行度；每次并行提速都验证并行度与质量不倒退。

05全生命周期流水线与质量 Gate

对应《AI 工程概论》的五阶段模型，映射到三域执行；每段输出进入一道质量 Gate，Gate 不通过，下一段不启动。五阶段：场景挖掘与需求分析 → 产品设计与方案架构 → 单点实现 → 多 Agent 编排与流水线 → 测试部署交付复盘。五阶段由项目管理域按 PDCA 四步循环驱动，每道质量 Gate 即 Check 节点，每步有量化反馈（进度 / Gate 通过率 / Token 消耗 / Bug 数 / 覆盖率）。

阶段① · 需求收敛

ProductAgent 执行需求深访：5Why 追问、行业速览（15 分钟输出行业架构与提效场景）、MoSCoW 输出需求清单并冻结基线。PRD 用三段式提示词（背景 + 约束 + 验收标准）生成，每条需求带可度量验收条件，做歧义检测。

阶段② · 方案蓝图

ArchitectAgent 从 PRD 生成架构图（JSON）、数据模型、接口定义（YAML），做任务拆包：每个任务包 ≤2 人天，含独立输入 / 输出契约与验收标准——这是后续并行编排的前提。

阶段③ · 单点实现

Coding 域用约束型提示词（角色 / 格式 / 边界 / 示例 / 反例 / 验收六类约束）+ 代码库上下文注入驱动；遇 Bug 执行「读 → 改 → 测」闭环，3 轮内归零。

阶段④ · 编排流水线

PMAgent 按契约并行编排 Backend / Frontend / Api 三席（并行耗时 ≤ 串行 50%）；联调后整体进入品控域。多项目并行时叠加资源调度、冲突避让、异常降级。

阶段⑤ · 交付复盘

QAAgent 执行四层测试与覆盖率计量 → ReviewAgent 独立评审 → DeployAgent 部署交付与文档生成 → DistillAgent 四维复盘并蒸馏 Skill / 模板入库，为下一个项目提速。

有罪推定（贯穿全程）

所有产出物——PRD、架构、代码、测试、文档——在下游 Agent 眼里默认不合格（有罪），拿出证据自证清白（合格）才放行。证据 = 测试报告 / 覆盖率报告 / 扫描结果 / 评审记录 / 冒烟结果 / 文档完整性核验。质量 Gate 采用有罪推定：证据不足即退回，而不是证据不足即放行。

06质量 Gate 细则

六道 Gate 是流水线的「硬闸门」，由 QAAgent 执行、ReviewAgent 复核、PMAgent 裁决、FDE 终审。Gate 采用有罪推定：所有产出物默认不合格，证据不足即退回——不是证据不足即放行。通过率目标 >90%；未过 Gate 的产物一律退回，不得携带进入下一段。

有罪推定原则：下游 Agent 对上游交付的每一份产出物持悲观态度——PRD、架构、代码、测试、文档无一豁免，默认都是不合格的。放行的唯一条件是证据自证清白；证据不足、存疑、缺环，一律退回上游并附缺陷清单，由产出方补齐证据后重跑 Gate。
产出物默认状态（有罪推定）自证清白的证据清白标准
PRD默认不合格歧义检测报告、MoSCoW 清单、可度量验收条件核验G1 通过
架构 / 契约默认不合格架构一致性检查、接口契约完整性核验、任务包契约核验G2 通过
代码默认不合格编译 / Lint / 单测自证报告、契约无漂移比对G3 通过
测试默认不合格四层测试结果、覆盖率 ≥95% 计量、可追溯矩阵G4 通过
文档默认不合格完整性 ≥90% 核验、与产物一致性比对、评审记录G6 通过

G-sec · 凭据泄露扫描 Gate（跨阶段安全闸 · ReviewAgent 执行）

  • 对每个阶段全部产物（PRD / 架构 / 代码 / 测试 / 文档 / 复盘记录 / 日志）执行凭据泄露扫描：明文账号、密码、API Key、Token、连接串等，命中一律拦截
  • 发现明文凭据 → 立即拦截放行并告警 FDE，退回产出方移除凭据、修复泄露点后重跑本 Gate
  • 凭据「用而不见」核查：Agent 的 prompt / 上下文 / 日志 / 复盘记录中不得出现任何凭据明文或部分明文
  • 扫描规则随 ai-assets 安全基线维护；命中记录计入失败数据，供 DistillAgent 复盘

G1 · 需求基线 Gate（入口闸）

  • MoSCoW 需求清单齐全，Must 类需求全部有可度量验收条件（数字 / 阈值 / 场景可判定）
  • 歧义检测通过：「危化品告警」类口语已挖至底层真实诉求（如分区联动应急处置），无未澄清术语
  • 需求基线冻结单签署，变更走显式变更流程（变更 → 重跑 G1）

G2 · 方案契约 Gate

  • 架构一致性检查通过：数据模型 / 接口契约 / 模块划分与 PRD 逐条可追溯
  • 接口定义（YAML）完整：字段、错误码、权限、幂等、并发语义齐全
  • 任务包全部 ≤2 人天，每个任务包含独立输入 / 输出契约与验收标准
  • 可复用资产检索完成：已有登录 / 权限 / 报表组件优先装载，而非重写

G3 · 编码合规 Gate

  • 编译通过、Lint 零违规、编码规约一致（代码库上下文注入校验）
  • 单元测试随代码同行（Backend / Frontend / Api 各自自证报告）
  • 凭据零穿透核查：无密钥进入代码 / 日志 / 上下文；敏感配置仅本地；G-sec 凭据泄露扫描零命中
  • 契约实现一致性：接口与 G2 契约无漂移

G4 · 四层测试 Gate（品控核心闸）

  • 单元 + 集成 + E2E + 性能四层测试全部运行
  • 测试代码业务覆盖率 ≥95%（需求 → 用例 → 代码 逐条映射）
  • E2E 覆盖核心业务路径；性能测试满足 SLA（并发 / 响应时间）
  • ReviewAgent 独立评审通过：代码走查、可追溯矩阵、安全扫描无高风险

G5 · 部署冒烟 Gate

  • 新环境部署 + 冒烟测试 ≤30 分钟（环境编排脚本化）
  • 冒烟用例覆盖关键链路：登录、核心业务流、健康检查端点
  • 回滚预案就绪（上一版本可恢复），上线窗口与客户确认

G6 · 交付验收 Gate（出口闸）

  • API 文档 / 运维手册 / 用户指南齐全，完整性 ≥90%（DeployAgent 产出）
  • 客户验收标准逐项核验（G1 的验收条件回环验证）
  • DistillAgent 四维复盘完成，≥3 条经验蒸馏入库；资产库提交已合并
  • FDE 终验通过 → 签发上线移交单

评估闭环：让流水线自我纠错

发现 → 修复 → 验证循环

Gate 拦截不合格产出后，不「报警等人来修」，而是自动触发对应修复 Agent（编码问题 → Coding 域；契约问题 → ArchitectAgent），修复后重跑 Gate，循环直到通过或达到最大重试次数；超限自动升级 FDE。

失败数据积累

每次问题的类型、位置、修复方式被记录。积累到阈值后自动分析：系统最常出哪类问题、哪个 Agent 需要加强——形成持续改进正循环，并为 DistillAgent 提供复盘输入。

回溯机制

下游发现问题可沿 Gate 追溯上游：接口契约漂移 → 查 G2；覆盖率缺口 → 查任务包验收标准。避免「最后测试没过，不知道是谁的锅」。

安全合规内建

凭据只在本地配置和使用，零穿透大模型服务，不进入任何 Agent 可见上下文；G3 与 G6 两次安全核查；Token 消耗按项目 / Agent 分组核算，成本透明。

07实施路线图

严格遵循「先立后破、先串后并」：先建资产与流程（立），再上红线与并行（破）；首期用一个需求稳定、ROI 最高的项目串行走通五阶段，再并行提速、规模复制，最后完成能力转移。

阶段 0 · 第 1–2 周

基建先行（先立）：资产库 + SOP 2.0 + Token 治理 + FDE 认证

  • 代码库 + Agent 库：建立目录结构（规约 / 模板 / 案例 / 组件库）、README 索引、Git + PR 管理；首批上架可复用 Agent（登录 / 权限 / 推送 / 报表导出）。
  • SOP 2.0：按四要素撰写首批面向 Agent 的 SOP——立项、需求深访、PRD 生成、任务拆包、编码规约、Gate 检查、部署。
  • 目录规范落地：建立 ai-assets 与首个项目仓库（双仓物理分离、各自独立 Git）；编写两仓根目录 OPCTEAM.md 与每层 README 索引；锁定「目录名即语义」命名规范与 .env.local 凭据红线。
  • Token 治理：按项目 / Agent 分组、额度管控、用量核算、计量看板上线。
  • FDE 培养：第一批 FDE 培训认证——问题拆解、Agent 指挥、结果验证、流程沉淀、持续迭代五项能力，实操考核过关持证。
  • 效果验收：随机抽人驱动同一 Agent 产出一致性达标，证明「不因人而异」成立。
阶段 1 · 第 3–6 周

串行试点：首个高 ROI 项目走通五阶段流水线

  • 选一个需求稳定、ROI 最高的新立项项目（如物流 EHS 平台二期模块）。
  • ProductAgent 深访 + MoSCoW 冻结基线 → G1；全程串行，十席逐个验证，不并行；每个阶段按 PDCA 四步走完（Plan 定目标 → Do → Check → Act），不得跳步、不得带病交付。
  • 跑通 G1 → G6 全链路，建立数据基线：AI 覆盖率、Gate 通过率、四层覆盖率、部署耗时、人均项目数。
  • 阶段门禁：Gate 通过率 >90%、覆盖率 ≥95%、部署 + 冒烟 ≤30 分钟——全部达标才进入下一阶段。
阶段 2 · 第 7–10 周

并行提速：Coding 域三席并行 + 多项目起步

  • 从 2 席并行开始（如 Backend + Frontend，契约先行），验证并行度与质量后再加 Api 席。
  • 目标：并行编排耗时 ≤ 串行 50%。
  • 启动第 2 个项目串行 + 第 1 个项目迭代并行，练习资源调度、冲突避让、异常降级、全景看板。
  • 每轮并行提速都用「随机抽人驱动 Agent 产出一致性」复查质量不倒退。
阶段 3 · 第 11 周起（持续）

规模复制与能力转移：1人/3项目+，组织自身具备工程化能力

  • 标杆资产包复制：把已验证项目的代码库结构、Agent 清单、SOP 模板打包，所有新立项项目装载资产包启动。
  • AI 覆盖率 70% → 90%+；人均项目数 1人/1项目 → 1人/3项目+。
  • 新人两周达到老人 80% 产出效率（依赖资产库 + SOP + Agent 库）。
  • 终局转移：FDE 工作方法与资产库运营能力转移给公司自有团队——公司自行具备工程化交付能力，不依赖外部 FDE。
  • 组织版本化 + 季度迭代：每季度复测 AI 原生度五维，版本号前进一个小版本，经验回写资产库。
反工程化风险提示：推行期可能出现两类阻力——「拒绝标准化」（业务特殊论、永远在试点）与「以招人堆产能」（流程缺口先增编）。应对机制：新增人力一律过「工程化前置评审」五问；计量看板只晾晒不评比；效果验收替代文件验收；治理靠数据不靠运动。

PDCA 四步循环Plan 定目标 → Do 按 SOP 执行 → Check 用 Gate 与五指标核验 → Act 达标放行并复盘；管理域不得跳步、不得带病交付，每步有量化反馈（进度 / Gate 通过率 / Token 消耗 / Bug 数 / 覆盖率）。
先立后破 / 先串后并先建资产与流程再上红线与并行；先用串行走通再用并行提速。
双仓架构组织级资产库 ai-assets 与项目级工作区 <project> 物理分离、各自独立 Git 仓库。
目录名即语义目录 / 文件名即契约：产物按阶段与职责归位，禁 misc / tmp 等无语义目录。
OPCTEAM.md 锚点仓库根目录的上下文锚点，Agent 进入即读：身份、边界、目录地图、SOP 指针、安全红线。
凭据用而不见凭据仅本地配置使用、零穿透大模型服务；Agent 可「使用」凭据但从不「看见」——凭据不入 prompt / 上下文 / 日志 / 复盘记录。
凭据泄露扫描 GateG-sec：ReviewAgent 对每阶段产物执行扫描，发现明文账号/密码/API Key/Token 即拦截放行并告警 FDE。
