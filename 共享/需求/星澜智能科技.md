# 需求

## 背景

- 星澜智能科技是一家五十人规模的软件定制开发公司，客户以物流、制造行业企业为主，典型项目包括物流 EHS 平台、设备监控系统、合规文档系统等；公司按产品、Coding、质检、项目管理四支职能团队串行接力交付定制系统。

## 痛点

- 星澜智能科技的编码交付，长期受制于「产品 / Coding / 质检 / 项目管理」四个职能团队之间的边界损耗，问题如下：
- 需求在层层翻译中失真：给物流客户做 EHS 平台，客户口头说的是「危化品告警」，写进 PRD 变成了通用阈值告警，上线演示当天才发现客户要的是分区联动的应急处置流程，就这一个词，返工近一个月；需求评审来回拉锯三四轮是常态。
- 编码在重复造轮子中内耗：登录、权限、消息推送、报表导出，每个新项目都从零重写一遍，粗算下来新项目里过半代码和上一个项目高度相似，但一直没人有余力把这些东西沉淀成可复用的资产。
- 测试在工期压力下被牺牲：排期一紧，先压缩的就是测试，只保核心路径过一遍；这两年交付的项目，不少在上线后头一两个月都是客户现场边用边修，售后返修吃掉了团队大量工时。
- 经验随人员流动而流失：去年一名核心开发离职，他手上几个项目的关键逻辑大多在他脑子里，接手的同事拖了一个多月才敢动第一个需求。

## 目标

- 以工程化方法重构交付组织形态——用一支 SubAgents 团队取代四支职能团队的串行接力，让一名 FDE 在两端（定义标准、验收结果）做判断，中间执行全部交给 Agent 按 SOP 完成。
- 目标形态：人均项目数从「N 人 / 1 项目」跃迁到「1 人 / 3 项目+」；编码交付环节的 AI 覆盖率从约 20% 提升到 70%，持续牵引至 90%+。

## 边界

- 覆盖范围：所有新立项的定制开发项目，从需求到部署全流程按新体系交付；存量项目维持现有维护模式，不回头改造。
- 前提约束：需求稳定是整套体系的前提，需求频繁变更的项目，先做需求深访、用 MoSCoW 冻结需求基线，再进入流水线。
- 实施节奏：先串后并——首期选一个需求稳定、ROI 最高的项目串行跑通五阶段流水线，并行编排与多项目并行放到后续阶段推进。
- 安全底线：所有账号、密码、API 密钥等凭据只在本地配置和使用，零穿透到大模型服务，不进入任何 Agent 的可见上下文。
- 终局要求：FDE 工作方法与资产库运营能力要转移给公司自己的团队，最终组织自身具备工程化交付能力。

## 验收

- 质量立场：每段产出默认不合格、以证据自证合格才放行，各段质量 Gate 通过率 >90%。
- 测试的代码业务覆盖率不低于 95%（单元 / 集成 / E2E / 性能四层测试）；新环境部署加冒烟测试 ≤30 分钟。
- 并行编排耗时 ≤ 串行耗时的 50%。
- AI 覆盖率：编码交付环节 20% → 70%，持续牵引 90%+。
- 人均项目数：N 人 / 1 项目 → 1 人 / 1 项目，最终 1 人 / 3 项目+。
- 不因人而异：换一个 FDE 驱动同一套资产库与流程，交付结果一致；新人两周达到老人 80% 的产出效率。
- 终验方式：选一个真实新立项项目完整走一遍五阶段流水线，以上各条逐项核验。
